# 연구 재구성 지시서 — 프로젝트를 논문으로 (Claude Code 작업용)

> 목적: 현악기 연주기법 분류 프로젝트를 "구현 완료 상태"에서 "논문 투고 가능 상태"로 재구성한다.
> 핵심 인식: 이 작업은 **새 실험을 추가하는 것이 아니라, 기존 결과를 하나의 연구 질문 아래 재배열하고,
> 통계적/방법론적 결함을 점검·수정하는 것**이 우선이다. 코드보다 재구성이 먼저다.

---

## 0. 작업 원칙 (반드시 먼저 읽을 것)

- 이 지시서는 "무엇을 만들지"가 아니라 "무엇을 검증하고 무엇을 재배열할지"에 관한 것이다.
- 각 작업을 시작하기 전에 **먼저 현재 코드/결과 파일을 읽고 실제 상태를 확인**한 뒤,
  "이미 되어 있는 것"과 "새로 해야 하는 것"을 스스로 구분해서 보고할 것.
- 결과를 좋게 포장하지 말 것. leakage나 cherry-picking이 발견되면 숨기지 말고 명확히 보고할 것.
- 각 섹션 끝나면 markdown 리포트로 요약할 것.

## 1. 최우선 — 방법론적 결함 점검 (코드 감사)

새 실험보다 먼저, 기존 파이프라인에 아래 4가지 함정이 있는지 **코드를 직접 읽어서** 확인하라.
하나라도 발견되면 그 즉시 보고하고, 수정 방향을 제안하라.

### 1-1. Self-training τ(threshold) 선택의 leakage 점검
- **확인 대상**: `results/phase1/`, `results/phase4/` 및 self-training 관련 스크립트
- **핵심 질문**: τ ∈ {0.7, 0.8, 0.9} 중 "최고 성능 τ"를 **어떤 데이터의 성능을 보고 골랐는가?**
  - test/holdout(Pool B) 성능을 보고 골랐다면 → **심각한 leakage**. test set에 튜닝한 것.
  - validation split에서 골랐다면 → 정상.
- **확인 방법**: τ를 선택하는 코드 라인을 찾아, 그 선택이 참조하는 성능 지표가 어느 split에서 계산되는지 추적.
- **결함 발견 시 복구**: train fold 내부에 validation split을 따로 만들어 거기서 τ를 고르고,
  test는 최종 1회만 평가하도록 재구성.

### 1-2. "Best fold" cherry-picking 점검
- **확인 대상**: "MERT + self-training (best) 0.920, 단일 fold, Vc fold" 라고 보고된 부분
- **문제**: 4개 fold 중 best fold만 보고하는 것은 cherry-picking.
- **수정**: 모든 결과를 **4-fold 평균 ± 표준편차**로 통일해서 재보고.
  단일 fold 수치는 본문에서 제거하거나 "best-case" 라고 명시적으로 강등.

### 1-3. Multiple comparison / 주 실험 vs 탐색 구분
- **확인 대상**: seed(4개) × τ(3개) × 모델(여러 개) 조합 전체
- **문제**: 수십 개 조합 중 좋은 것만 부각하면 다중 비교 오류.
- **수정**: "사전에 정한 주 실험(primary)"과 "탐색적 실험(exploratory)"을 명확히 구분하는
  표를 만들 것. 논문 본문은 primary만, 나머지는 supplementary.

### 1-4. 통계적 유의성 검정 부재
- **현재**: "self-training +3.8%p 향상" 등의 주장에 유의성 검정이 없음.
- **추가**: LOSO fold별 점수 쌍(baseline vs self-training 등)에 대해
  **Wilcoxon signed-rank test** 또는 paired t-test 수행.
- **판단 기준**: 향상폭이 fold 간 표준편차 안에 들어가면 "유의하지 않음"을 정직하게 보고.

## 2. 연구 서사 재구성 (실험 재배열, 새 실험 없음)

### 2-1. 단일 연구 질문(Research Question)으로 통합

현재 문제: 기여가 4개로 분산(self-training / ALM 한계 / SHAP / cross-domain)되어
"핵심 주장이 무엇인가"가 불명확함. 논문은 하나의 질문 + 그것을 지지하는 여러 실험이어야 함.

**채택할 단일 연구 질문(RQ)**:
> "세밀한 현악 연주기법 분류에서, 범용 대형 오디오 모델(SSL 기반 MERT, ALM 기반 Qwen2-Audio)은
> 언제·왜 도메인 특화 수동 특징(hand-crafted features)에 뒤지는가?"

### 2-2. 기존 결과를 RQ의 하위 근거로 재배열

기존 실험을 하나도 버리지 말고, 아래 역할로 재배치하라:

| 기존 Phase | 재배열 후 역할 |
|---|---|
| SVM > MERT > ALM 성능 순서 | **답의 본체** (현재 표에 묻혀 있음 → 전면 배치) |
| Phase 3 SHAP flux 분석 | **왜 그런지에 대한 음향학적 설명** |
| Phase 4 cross-domain | **격차가 도메인 이동에서 어떻게 벌어지는가** |
| Phase 1 self-training | **격차를 좁히려는 시도와 그 구조적 한계** |
| Phase 2 ALM 환각 | **대형 모델 실패의 정량적 근거** |

### 2-3. 재구성된 논문 아웃라인 생성
위 재배열을 반영한 논문 섹션 아웃라인(Introduction → RQ → Method → 각 실험 → Discussion)을
markdown으로 작성하여 `docs/paper_outline.md`에 저장하라.

## 3. 반드시 보완해야 할 연구 설계 요소

### 3-1. 클래스 선택 정당화 (Introduction/Method에 추가)
- **문제**: "왜 이 5개 주법(ordinario/tremolo/pizzicato_secco/sul_ponticello/col_legno_battuto)인가?"에
  대한 근거가 없음. 리뷰어가 반드시 물음.
- **작업**: 이 5개가 활-현 상호작용의 물리적으로 구분되는 모드를 대표한다는 음향학적/음악적 근거를
  정리. OrchideaSOL의 전체 주법 목록과 비교해 "왜 이 부분집합인가"를 명시.

### 3-2. 진짜 Error Analysis (결과 보고가 아닌 원인 분석)
- **현재**: "col_legno F1 낮음" = 결과 보고에 그침.
- **작업**:
  1. 오분류된 샘플의 confusion 방향 분석 (col_legno가 **무엇으로** 오분류되는가)
  2. 오분류 샘플들이 공유하는 음향적 특징을 SHAP/feature 분포로 추적
  3. 대표 오분류 사례 3~5개를 case study로 문서화
- **저장**: `results/error_analysis/`

### 3-3. Ordinario 포함/제외 두 버전 결과
- 메인: 5클래스 전체
- 보조(supplementary): ordinario 제외 4클래스
- 목적: "ordinario가 많아서 F1이 높은 것 아닌가"라는 공격 선제 차단 + 더 어려운 세팅 검증

## 4. Evaluation 보강

### 4-1. Phase 2 ALM 평가 표본 확장 (최우선 결함)
- **문제**: 125샘플(25/class)은 통계적으로 취약. 클래스당 신뢰구간 ±20%p 수준.
- **작업**: Y/N 질문을 OrchideaSOL 전체(3,402개)로 배치 확장 실행.
  open-ended는 속도 문제로 125개 유지 가능하나, 그 한계를 논문에 명시.
- **사전 확인**: 3,402개 배치 실행이 Qwen2-Audio 추론 속도로 현실적 시간 내 끝나는지
  먼저 10개 샘플로 소요 시간 측정 후 총 시간 추정 보고.

### 4-2. Phase 1 SVM seed별 성능 추가
- **문제**: SVM은 50% seed(0.916)만 있고 5/10/20% 성능이 없어 "foundation model이
  언제 유리한가"의 교차점을 못 보여줌.
- **작업**: SVM을 seed 5/10/20/50%로 제한 학습 + 동일 LOSO 평가.
- **기대**: 낮은 seed에서 MERT+ST > SVM 교차점이 나오면 "제한 라벨 환경에서 foundation model
  효용"이라는 핵심 결론 완성.

### 4-3. Phase 3 방향성 수치화
- flux_std의 클래스별 기술통계(mean/std/median) 테이블 + 박스플롯 생성.
- "낮다/높다"를 실제 측정값으로 뒷받침.

## 5. 인과관계 확보 (선택적, 여력 있으면)

### 5-1. 개입 실험 (Phase 2-3 연결을 상관→인과로)
- **현재**: "ALM이 tremolo 못 하는 건 temporal flux 못 잡아서" = 순수 추측.
- **작업**: ordinario 클립 10~20개에 spectral flux를 인위적으로 변조한 버전 생성 →
  Qwen2-Audio에 재질문 → 답이 tremolo 쪽으로 이동하는지 확인.
- **주의**: 합성 신호가 "진짜 연주가 아니다"라는 지적 대비, 변조를 최소한으로 하고
  변조 전후를 청취 가능한 샘플로 함께 공개.
- **미수행 시**: 해당 인과 문장을 전부 "가설(hypothesis)"로 명확히 강등할 것.

## 7. 작업 순서 (권장)

```
STEP 1 (감사, 최우선): 섹션 1 전체 — 코드 읽고 leakage/cherry-picking 점검 → 보고
STEP 2 (재구성): 섹션 2 — 단일 RQ 확정 + paper_outline.md 생성
STEP 3 (핵심 실험): 4-1(ALM 확장) 사전 시간측정 → 4-2(SVM seed) → 4-3(flux 수치)
STEP 4 (설계 보강): 3-1(클래스 정당화) + 3-2(error analysis) + 3-3(4클래스 버전)
STEP 5 (통계): 1-4 유의성 검정 전체 적용
STEP 6 (선택): 5-1 개입 실험
STEP 7 (재현성): 섹션 6 정리
```

**STEP 1을 먼저 하라.** leakage가 발견되면 이후 모든 결과의 신뢰성이 바뀌므로,
재구성·보완보다 감사가 절대적으로 우선이다.

## 8. 하지 말아야 할 것

- 결과를 좋게 포장하지 말 것. 특히 leakage/cherry-picking 발견 시 은폐 금지.
- "단일 fold best" 수치를 대표 성능처럼 쓰지 말 것.
- 유의성 검정 없이 "향상되었다"고 단정하지 말 것.
- 인과 검증(개입 실험) 없이 인과 문장을 쓰지 말 것.
- 새 실험을 벌이기 전에 반드시 STEP 1 감사부터 끝낼 것.
